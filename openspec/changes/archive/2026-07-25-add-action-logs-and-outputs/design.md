# Design: Add Action Logs and Outputs

## Context

The action writes diagnostic information through direct calls to `core.info`, `core.warning`, and `core.error`. This is adequate for human inspection but does not give calling workflows or log aggregators structured, machine-readable data. In addition, the action does not expose review outcomes as GitHub Action outputs, so downstream steps cannot branch on verdicts, counts, or session IDs without parsing PR comments.

This change adds a small, internal logging layer and emits a stable set of action outputs. It keeps using only `@actions/core` so the repository maintains its lean dependency footprint and GitHub UI log behavior stays unchanged.

## Goals / Non-Goals

**Goals:**

- Emit structured JSON log events for major lifecycle stages and API calls.
- Make review results available as action outputs for downstream workflow automation.
- Keep the implementation dependency-free.
- Continue to scrub secrets and untrusted inputs from logs and outputs.
- Cover the new behavior with tests that preserve the existing coverage threshold.

**Non-Goals:**

- Reformatting or enhancing the PR review comment output.
- Adding remote metrics, dashboards, or external observability integrations.
- Changing the prompt or the Jules review model behavior.
- Adding configurable log levels or verbose modes.

## Decisions

### Use a custom structured-logging helper instead of a third-party logger
- **Rationale**: `@actions/core` already provides the primitives needed (`core.info`, `core.error`, `core.setSecret`, `core.setOutput`). A dedicated library would add dependencies and bundle size for marginal value. A thin wrapper keeps the bundle small, respects existing formatting rules, and avoids conflicting with Actions log groups and annotations.
- **Alternative considered**: Winston was discussed, but it introduces a runtime dependency and different log formatting. Rejected to keep the change minimal and aligned with GitHub Actions conventions.

### Prefix structured entries with `::structured::` and emit via `core.info`
- **Rationale**: GitHub Actions captures `core.info` output in the run log. A stable prefix lets consumers parse structured events from the log stream with simple text matching while keeping the entry visually identifiable. It also leaves the human-readable log intact and does not interfere with `::group::`, `::error::`, or other Actions commands.
- **Alternative considered**: Writing structured logs to a separate file. Rejected because GitHub Actions does not persist arbitrary files by default and workflows already have access to the run log.

### Place log setup, structured logging, and output helpers in a new `src/logging.ts` module
- **Rationale**: Isolating the capability in one module follows the Single Responsibility Principle and makes instrumentation points in `src/index.ts` concise. It also centralizes secret scrubbing logic and creates a clear surface for tests.

### Compute issue counts from the Jules response before formatting comments
- **Rationale**: Counts must be based on the parsed `ReviewResult` so they reflect the same data used to submit the review. Computing them before filtering suggestions keeps the output consistent with what was sent to GitHub.

### Set outputs inside the main `try` flow and in the early-skip branches
- **Rationale**: Workflows that reference `steps.jules.outputs.verdict` should always receive a defined value. Setting it in every exit path prevents downstream steps from receiving undefined values when drafts, forks, or bypass labels cause early returns.

## Risks / Trade-offs

- **[Risk] Log bloat in the GitHub UI** → **Mitigation**: Only one structured line per major stage (start, diff fetched, API call complete, review complete/failed). No per-comment or per-file lines are emitted.
- **[Risk] Secrets leaked through structured events** → **Mitigation**: All values pass through a scrubber that masks tokens. The helper never emits raw `apiKey`, `token`, diff text, PR titles, or PR bodies. `core.setSecret` is called on inputs as before.
- **[Risk] Output schema changes over time break downstream workflows** → **Mitigation**: The initial outputs are additive and named clearly. The README documents them as stable. Breaking changes would be marked as such in future proposals.
- **[Risk] Output values derived from untrusted Jules response** → **Mitigation**: Outputs use only categorical fields (`verdict`), counts, and the session identifier. The free-text review summary is already generated by the model but could still contain surprising content; we will not surface it in outputs unless explicitly requested later.

## Migration Plan

No migration is required. Existing workflows continue to work because the change only adds outputs. Consumers can optionally reference the new outputs after upgrading.

## Open Questions

- Should `review_url` be included as an output? The action currently does not keep the submitted review URL returned by GitHub, so adding it would require an extra API response ingestion. Left out for now to keep scope small.
- Should the structured log include a stable schema version field? It may be useful for future consumers but is not strictly required for the current use cases. This can be revisited when external tooling starts parsing the prefix.
